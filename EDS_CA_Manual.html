Instructor & Course Assistant Manual

Helping every student get unstuck

This manual supports Course Assistants and STEM Leadership Fellows working Elements of Data Science (SCTC 1013) — a first-year course that teaches Python, data wrangling, and statistical inference to roughly 550 CST students a year. It covers course policies, the coding and statistical content you'll be asked about most, and practical strategies for supporting students in class and during office hours.

Student-facing policies

What follows is what students are held to — know it well enough to answer a policy question the same way the instructor would, without needing to check the syllabus live.

Grading & late work

Grade components and their exact weights are detailed in the syllabus (they can shift slightly term to term), but the components themselves are consistent: weekly lab assignments, quizzes, attendance/participation, group activities, and a culminating group project and presentation. Point students to the current syllabus for exact percentages rather than quoting a number from memory.

Late lab policy — confirm the exact penalty with your instructor A student gets an automatic 2-day extension at a percentage penalty — but don't quote a specific number from memory, since this has varied by term (10% in some past terms, 20% in others). Check the current syllabus or confirm with your instructor before telling a student a figure. What is consistent: anything submitted more than 48 hours after the due date receives no credit — Canvas locks submissions at that point, no exceptions — the lowest lab score is dropped, and non-submission counts as a zero (so encourage students to submit something rather than nothing).
Quizzes & mini-tests No make-ups are granted for a missed quiz, and the student's lowest quiz score is typically dropped. The format itself varies by instructor: some quizzes are taken online via the Hub and draw a random subset of questions from a larger bank (so two students in the same room may see different questions — don't assume a shared question set when helping); others are administered on paper in class with a single shared question set. Check which format your section uses before describing it to students.

Submitted work should include comments (#) and markdown explaining reasoning, similar to showing work on a math problem. Encourage students to break complicated code into multiple cells rather than one dense block — this is graded on and also makes debugging with them much easier.

Academic honesty

Classmates may discuss data and coding challenges together, but submitted work must be the student's own. Cheating on any graded component results in a zero — and the penalty is the same whether the work was copied from or by the student, so remind students that "just letting a friend see it" carries real risk for both parties.

Generative AI policy

What the syllabus says Using generative AI to complete lab exercises is discouraged: it negates the point of the exercise, tends to produce code that's hard for the student to modify or debug, and leaves them without the understanding they'll need on quizzes. The course also uses a custom datascience Table API that most generative AI tools were not trained on well, so AI-written code frequently doesn't match what the course actually teaches. Generative AI is considered acceptable as a background tutor — explaining a Python concept like loops or variables — but not for producing assignment answers.

As a CA, this is a useful line for students who show up with AI-generated code that "doesn't work": point out that it likely isn't using the datascience Table or the course's conventions, and walk them back to the lab's own pattern instead of debugging the AI's code line-by-line.

This tell isn't foolproof A student who explicitly prompts the AI to "use the datascience Table library, not pandas" will get code that looks like the course's own conventions — so a mismatch with Table syntax is a useful signal but not a reliable test on its own. The more durable approach is the same one used elsewhere in this manual: ask the student to explain what a given line does, or how they'd approach the problem on paper first (see the math skills note in Section 2). Code a student can't explain is the real signal, regardless of whether it happens to use the right library.
Section 2

Coding Review

A refresher on the Python and course-specific constructs students will be using early in the semester. Most incoming students have never coded before (see the survey data in Section 5) — expect to explain basic syntax patiently and often. This course leans much more heavily on the datascience Table plus np.arange() and np.array() than on other array-building shortcuts — keep your own explanations centered on those.

The datascience Table

The are. predicate family used inside .where() is worth knowing by heart: are.equal_to(v), are.above(v), are.below(v), are.between(a, b), and are.not_equal_to(v).

A genuinely tricky one: .sample(n) vs. .sample() With an argument, .sample(100) draws 100 rows with replacement. Called with no argument at all, .sample() still samples the whole table, with replacement — it does not just return the table unchanged. This surprises students (and CAs) constantly, especially in bootstrap contexts where that behavior is exactly the point but rarely obvious on first read.

If a student's error mentions DataFrame or .loc[], they've likely copied pandas syntax from a generic tutorial or AI tool — redirect them to Table methods, since this course does not use pandas by default.

Booleans, conditionals, and loops

Start any Boolean-filtering explanation with the actual array in front of the student — the pattern is much less cryptic once they can see what's being compared:

arr = np.array([1, 5, 7, 8, 3, -1])
mask = arr > 3
print(mask)                    # array([False, True, True, True, False, False])
np.count_nonzero(mask)         # 3  -- counts the True values

The accumulator pattern below (initialize outside the loop, update inside it) is the single most-reused structure in the course — from radiation-dose totals in Lab 5 to the Monte Carlo simulations used throughout the statistics module:

total_dose = 0                      # initialize accumulator
for i in np.arange(num_trips):
    dest = np.random.choice(destination)
    dose = calculate_dose(dest)
    total_dose = total_dose + dose  # accumulate

np.arange() and np.random.choice() in depth

These two functions alone cover most of what students need for loops and simulation, and it's worth being fluent in their full signatures rather than just the one-argument form:

CallBehaviorExample
np.arange(b)b-element array starting at 0np.arange(7) → [0,1,2,3,4,5,6]
np.arange(a, b)Array from a up to (not including) bnp.arange(1,7) → [1,2,3,4,5,6]
np.arange(a, b, s)Array from a to b, stepping by snp.arange(0,10,2) → [0,2,4,6,8]
np.random.choice(arr)One random element from arr (with replacement, single draw)np.random.choice(np.arange(1,7)) → e.g. 5
np.random.choice(arr, n)n random draws from arr, with replacement by defaultnp.random.choice(np.arange(1,7), 5) → e.g. [5,3,6,1,3]
Tricky example 1 — the classic dice off-by-one A student modeling a 6-sided die often writes np.random.choice(np.arange(1,6)) — this only ever returns 1 through 5, because np.arange(1,6) stops before 6. A fair die needs np.arange(1,7). This exact mistake shows up anywhere students model dice, cards, or 1-indexed categories.
Tricky example 2 — does np.random.choice sample with or without replacement? By default, with replacement — the same element can be drawn more than once, even within a single call like np.random.choice(suits, 6). Students modeling something that should not repeat (dealing distinct cards, assigning people to unique groups) need to know this default doesn't match their intuition, and that avoiding repeats requires an explicit replace=False or a different sampling approach entirely.

Math skills variability

Math preparation among incoming students varies enormously, and this is a bigger factor in coding struggles than it first appears. A student who can't translate "probability of A and B" into code usually isn't stuck on Python syntax — they're stuck on the math itself, and the code is just where that gap becomes visible. Watch for this especially in the probability, correlation, and regression material, where the code is short but leans on a formula the student may not actually understand.

A habit worth teaching early Before a student writes any code, ask them to work out how they'd solve the problem on paper — by hand, with actual numbers, no variables. If they can't do that, more time spent on the code won't help; the fix is a quick math refresher, not another syntax explanation. If they can do it on paper, translating it into code becomes a much smaller, more mechanical step, and debugging becomes easier for both of you since you can point at exactly which line doesn't match their own by-hand approach.

Common student errors to watch for

01

Ellipsis left in place

Labs use ... as a fill-in-the-blank. Students sometimes leave it and get a SyntaxError — check for stray ... first.

02

Comparing with =

Using assignment (=) instead of comparison (==) inside an if.

03

Off-by-one with np.arange()

Confusing np.arange(n) (stops at n−1) with wanting n as an inclusive endpoint — see the dice example above.

04

String vs. category mismatch

Typing 'yes'/'Yes' inconsistently when comparing to table columns — case sensitivity trips students up constantly.

05

Forgetting to return

Writing the right logic inside a function but never returning the value.

06

Re-running cells out of order

Especially on quizzes/labs with locking behavior — remind students to Restart & Run All before submitting.

07

Assuming .sample() is a no-op

Calling .sample() with no argument still resamples the whole table with replacement — see the callout above.

08

Mixing up array vs. Table return types

.column() returns an array; .select() returns a Table. Passing a Table where a function expects an array (e.g. into np.average()) is a very common source of cryptic errors.

Two matplotlib interfaces exist — worth naming explicitly The plt.scatter(...), plt.xlabel(...) style above is the implicit (pyplot) interface — it quietly tracks a "current" figure/axes behind the scenes, which is exactly why it's approachable for a first-semester student. The explicit (object-oriented) interface — fig, ax = plt.subplots() then ax.scatter(...), ax.set_xlabel(...) — is what most professional codebases and current online examples actually use, and it scales much better once a student wants multiple subplots or more control. It's also harder for a beginner to parse at first, which is why this course leans on the pyplot style early on. Worth flagging to a stronger student who's confused why their AI-generated or googled example looks different from the lab's own code — they're not wrong, they're just looking at the other interface. See Effective Matplotlib for a good side-by-side comparison.
Section 3

Data Wrangling

How students go from a raw .csv to something they can plot, filter, and reason about — the throughline of Module 1 and the backbone of every later lab.

The core workflow

  1. Load — Table.read_table('file.csv') from a local file or URL.
  2. Inspect — view the table, check .num_rows, column names and types.
  3. Filter — .where(column, are.equal_to(value)), or numeric predicates like are.above(x).
  4. Select / reshape — .select() to keep specific columns, .group() to aggregate, .sort() to order rows.
  5. Combine — .append() to stack rows from two filtered tables (used heavily to build "correct prediction" subsets, e.g. in the groundhog lab).
  6. Visualize — .hist(), .scatter(), or .plot() methods built into Table.
Where this shows up on the syllabus Lab 03 (Environmental Protection Index) is students' first real exposure to loading a .csv and using Table methods. Lab 04 (COVID/RSV/Influenza wastewater data) adds writing their own functions and visualizing time trends. Both are good labs to point struggling students back to as a refresher before Labs 05–07, which assume this workflow is already comfortable.

Helping students debug wrangling problems

  • Ask them to print the table (or .show(5)) before and after each step — most wrangling bugs are visible the moment you look at intermediate output.
  • Check column name spelling/case — .where() fails silently or errors confusingly if the column name is slightly wrong.
  • Confirm they're filtering before aggregating, not after — a common conceptual error when a group-then-filter and filter-then-group produce different (and both "reasonable-looking") results.
Section 4

Statistics

The conceptual core of Module 2 and 3 — probability, simulation-based inference, regression, and classification. These ideas are new to almost every student, so expect to re-explain them more than once, in more than one way.

Sample vs. population, probability & simulation

Almost every stats misunderstanding CAs untangle traces back to one distinction: a population is the entire group of interest (all groundhogs that have ever been observed, every possible dice roll); a sample is the subset actually in hand (the 33 groundhogs in the dataset, the 100 dice rolls just simulated). A population value is called a parameter; the corresponding value computed from a sample is a statistic. A sample statistic is an estimate of the population parameter, and — critically — a different sample would give a slightly different statistic purely by chance. That variability from sample to sample is exactly what simulation is built to characterize.

IdeaHow it's taught
Population vs. samplePopulation = everything; sample = what was actually observed or drawn
Parameter vs. statisticParameter describes the population (usually unknown); statistic is computed from the sample (known, but variable)
ComplementP(not A) = 1 − P(A)
IndependenceP(A and B) = P(A) × P(B) — knowing A tells you nothing about B
Monte Carlo simulationRepeat a random process many times (typically 1,000×) and look at the distribution of outcomes
Why 1,000 simulations, not 1? A single simulation is just one random draw and tells you little on its own. Repeating it many times builds a sampling distribution — the full range of what pure chance can produce. More simulations narrow the uncertainty in the estimated p-value; 1,000 is a practical compromise between precision and compute time. This is worth walking through visually with students who ask "why not just run it once?"

Simulation-based hypothesis testing

Statement
Null (H₀)The effect students are testing for is no better than random chance
Alternative (H₁)There is a real effect

Students are taught they can only ever reject H₀ — never "prove" H₁. The p-value is the probability of a result at least as extreme as what was observed, assuming H₀ is true. The course uses a shared interpretation scale:

p-valueInterpretation
> 0.05Insufficient evidence to reject H₀
≤ 0.05Suggestive evidence against H₀
≤ 0.01Strong evidence against H₀

Mechanically, this is always the same four-step recipe, whether it's groundhogs or anything else:

  1. Simulate many outcomes as if H₀ were true (e.g. random guessing) — this builds a synthetic population of "what chance alone can produce."
  2. Compute the same test statistic on each simulated outcome, building up a distribution of statistics under H₀.
  3. Compare the actually observed test statistic (from the real sample) to that distribution.
  4. The p-value is the proportion of simulated outcomes at least as extreme as the observed one — the shaded tail below.

The teal bars are the synthetic sampling distribution built by simulation; the maroon bars and dashed line mark the region at least as extreme as the observed statistic. A p-value is exactly the fraction of the teal+maroon area that is maroon.

"If the red dot sits well inside the distribution → H₀ not rejected. If it sits in the far tail → reject H₀."

One-tailed vs. two-tailed tests

The groundhog p-value above only counts simulated outcomes at or above the observed accuracy — that's a one-tailed (directional) test, appropriate because the question was specifically "are groundhogs better than chance," not "different from chance in either direction." A two-tailed test is for non-directional questions — "is this coin biased at all?" rather than "is this coin biased toward heads?" — and counts outcomes in both tails of the null distribution as evidence against H₀.

Why this trips people up Switching between one-tailed and two-tailed roughly doubles or halves the resulting p-value for the same data, since a two-tailed test spreads the same 5% threshold across both ends of the distribution instead of concentrating it in one. If a student's p-value doesn't match yours on the same dataset, check whether you're both counting the same tail(s) before assuming a coding error. The right choice depends entirely on how the question was phrased — directional claims get one tail, "is there any effect at all" claims get two.

The multiple comparisons problem (a good stretch topic for strong students)

Running several hypothesis tests on the same data inflates the false-positive rate: with 3 independent tests at α = 0.05, P(at least one false positive) = 1 − 0.95³ ≈ 0.143 — nearly triple the intended 5%. The Bonferroni correction addresses this by dividing the significance threshold by the number of tests run (α_adjusted = α / n_tests). This is a useful concept to have ready if a student notices "wait, didn't we just get lucky testing 33 groundhogs individually?" — that instinct is exactly the point of the lesson.

"Significant" doesn't mean "important" — effect size

This is worth being deliberate about, because the everyday meaning of "significant" (big, important, worth caring about) actively misleads students about what the statistical term means. Statistical significance only answers "how likely is a result this extreme to happen by chance" — it says nothing about how large or practically meaningful the effect actually is. With a large enough sample, even a tiny, real-world-irrelevant difference can produce a very small p-value.

The question to teach alongside the p-value Whenever a student reports "p < 0.05, so it's significant," follow up with: how big is the actual effect, and does that size matter here? That second question is about effect size — a measure of the magnitude of a relationship or difference, independent of sample size. Conveniently, this course already has one on hand: the correlation coefficient r (Section 4, Regression) is itself an effect-size measure, not just a significance test — an r of 0.05 can be statistically significant with enough data while still describing a relationship too weak to act on. Treat significance and effect size as two separate questions a result has to answer, not one.

Regression, bootstrap confidence intervals, and kNN classification

  • Correlation & regression — used in Lab 08 (Old Faithful: variance of sample means and correlation) and Lab 09 (estimating the age of the universe from the slope of supernova speed vs. distance).
  • Bootstrap confidence intervals — resampling the observed data (with replacement) many times to quantify uncertainty in an estimate, e.g. producing a 95% interval for the age of the universe from repeated slope estimates.
  • k-nearest neighbors classification — introduced with the iris flower dataset, then applied to a genuine research question: predicting molecular acidity (pKa) using Euclidean distance between chemical attribute vectors, drawing on real pKa data from Temple's Chemistry department.
# Euclidean distance — the core kNN building block
d_p_q = np.sqrt(sum((np.array([2,3]) - np.array([4,3]))**2))

def distance(pt1, pt2):
    """The distance between two points, represented as arrays."""
    return np.sqrt(sum((pt1 - pt2)**2))

Students often confuse "distance" as a physical concept with "distance" as a similarity metric across arbitrary attributes (e.g. molecular weight and pKa together) — a quick diagram of two points in 2-D space, then generalizing to "more dimensions, same idea," is usually the fastest way to unstick this.

Section 6

Teaching Foundations

The learning-science ideas behind the strategies in Section 5 — why roaming the room, normalizing errors, and asking rather than telling actually work, and what it means to treat the CA/Fellow role itself as a form of leadership.

What motivates students to learn

Ambrose and colleagues' model of student motivation gives CAs a useful diagnostic vocabulary for why a student is or isn't engaging with a lab, beyond "they're not trying." Two factors combine to produce motivation:

  • Value — whether the student sees the goal or outcome as worthwhile.
  • Expectancy — whether the student believes they can actually achieve it. Value alone isn't enough: a student who cares about the material but doesn't believe they can succeed at it will still disengage.

Value and expectancy together drive motivation, which leads to goal-directed behavior, which in turn supports learning and performance.

Efficacy — a second lever inside expectancy Efficacy is the student's belief in their own ability to produce the intended result. Crossed with whether the classroom environment feels supportive, and whether the student sees value in the task, this produces recognizably different student postures: a student with low efficacy in an unsupportive environment who doesn't see value looks rejecting; the same low-efficacy student who does see value looks hopeless rather than rejecting. A high-efficacy student in a supportive environment who sees value is motivated — the target state. The same high-efficacy student in a supportive environment who doesn't yet see value looks evading, not hopeless or rejecting.
Teaching leverValue — connect the lab to something the student already cares about (a real dataset, a visible result, a question they asked). Several labs already do this deliberately — molecular acidity prediction ties directly into Chemistry coursework, for instance.
Teaching leverEfficacy / expectancy — give the student direct evidence they can succeed: point to a smaller win before the harder question, or show them the same error you just normalized was fixable two labs ago.
Teaching leverEnvironment — this is largely in the CA's hands moment to moment. A roaming, non-judgmental, question-first presence is what turns "low efficacy + doesn't see value" from rejecting into merely hopeless, and — over a semester — toward motivated.

Practically: when a student seems checked out, it's worth silently diagnosing which lever is missing before deciding how to intervene. A student who says "this is pointless" has a value problem; a student who says "I just can't do this" has an efficacy problem — and they call for different responses from a CA, not the same generic encouragement.

A checked-out student may not have a motivation problem at all Sometimes a student who looks disengaged isn't lacking value or efficacy for the lab itself — they're using the in-class work time to study for an upcoming exam in another course entirely, treating lab time as a de facto study hall because the lab feels resumable later while the other exam doesn't. The Value/Expectancy/Environment model above still applies, but the lever being pulled is a competing one outside this class — it's a prioritization problem, not a value or efficacy problem with the lab. The Ambrose framework doesn't have much to say about this directly, and it isn't really solvable by making the lab more appealing. What tends to help is naming it plainly and making the cost of deferring visible — reminding the student what's actually due when, and that lab time not used now becomes harder time to find later — rather than trying harder to motivate them on the content itself.
Source: Ambrose, S. A., Bridges, M. W., DiPietro, M., Lovett, M. C., & Norman, M. K. (2010). How Learning Works: Seven Research-Based Principles for Smart Teaching. Jossey-Bass — Ch. 3, "What Factors Motivate Students to Learn?"

The hierarchy of learning

Bloom's taxonomy of cognitive skills gives a useful check on what level a lab question — or a student's difficulty — is actually operating at. Skills build from concrete recall up to independent creation, and most of the frustration CAs see comes from a mismatch: a student stuck at "remember" being asked an "analyze" question.

RememberRecall syntax and definitions — what np.arange() does, what a p-value is.
UnderstandExplain a concept in their own words — why a p-value is not "the probability H0 is true."
ApplyUse a known method on a new dataset — running the same accumulator-loop pattern on a new simulation.
AnalyzeBreak a result into parts and relate them — reading a histogram of simulated outcomes against an observed value.
EvaluateJudge the quality or validity of an approach — deciding whether three hypothesis tests on the same data need a Bonferroni correction.
CreateDesign something new — the final group project, where students choose a dataset, question, and method themselves.
Why this matters for CAs If a student can't get an "analyze" or "evaluate" question, first check whether they've actually got the "remember" and "understand" layers solid — jumping straight to re-explaining the harder question usually doesn't stick if the foundation underneath it is shaky. This is also why the reference tables scattered through Section 2–4 of this manual exist: they're the "remember" layer a student can be pointed back to quickly.
Source: Bloom, B. S. (Ed.). (1956). Taxonomy of Educational Objectives: The Classification of Educational Goals, Handbook I: Cognitive Domain. David McKay; revised by Anderson, L. W., & Krathwohl, D. R. (Eds.). (2001). A Taxonomy for Learning, Teaching, and Assessing. Longman.

The teacher as leader

Course Assistants in this program are STEM Leadership Fellows by name, but the leadership framing applies to every CA regardless of title. The role isn't "junior instructor" — it's closer to peer leadership: someone a student is more willing to be vulnerable and uncertain in front of than they might be with faculty, and whose job is specifically to unlock what a student is already capable of rather than to direct or evaluate them.

"Leadership is unlocking people's potential to become better."— Bill Bradley
A leader earns authority through understanding and trust, rather than demanding it the way a boss demands obedience.— paraphrased from Klaus Balkenhol
"You manage things; you lead people."— Grace Murray Hopper
The best leaders lead from within the people they're leading, not from above them.— paraphrased from M. D. Arnold

Read against the motivation model above, this is a fairly literal description of the CA job: a CA's presence in the room is itself part of a student's "environment" lever, and how a CA responds to a stuck, anxious, or checked-out student is often what determines whether that student experiences the class as rejecting, hopeless, or — with the right support — genuinely motivated. Leading a student well, in this specific sense, looks less like supplying answers and more like the peer-instruction habits already in Section 5: asking before telling, normalizing failure, and being visibly present rather than authoritative.

Quotes compiled from: HubSpot, "10 Inspirational Leadership Quotes to Motivate Your Team" — blog.hubspot.com/marketing/leadership-styles.

Test Yourself

Two self-check quizzes spanning this entire manual — good for your first week, and good to revisit anytime. Each pulls the freshest version of the quiz directly from the course repo, so you're never working from a stale copy.

How the attempts work Each quiz draws 30 questions at random from a bank of 50, and you get 3 attempts at the whole quiz — each attempt pulls a fresh set of 30, not the same ones again, so retaking is real practice rather than memorizing one fixed set. Re-running the quiz cell mid-attempt (say, after a kernel restart) always resumes where you left off — it does not use up a new attempt. A new attempt only starts once you've fully finished the previous one. Review the relevant manual sections between attempts rather than immediately retaking — that's the point of having more than one try.
